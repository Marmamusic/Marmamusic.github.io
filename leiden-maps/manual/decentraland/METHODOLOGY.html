Main-code communities, contextual layers and conversation profiles

Decentraland · Version 3, adjustable support and outlier extension · 8 October 2026

Purpose and classification

This version uses the entire edited DCL code workbook. Sheet1 supplies main codes and Sheet2 supplies contextual codes. The user's latest instruction explicitly includes all remaining main-sheet codes, including rows marked To classify. The status column is consequently retained as review history and does not determine inclusion. The code referred to as decentral_dao is spelled decentra_dao in the source. It is moved back into Sheet1 by descending conversation coverage, then message count, without renaming its descriptor label. No other code changes category.

There are 3,921 main codes and 117 contextual codes. All 4,038 labels and their source counts are checked against the normalized JSON. Only main codes determine the community partition, attraction forces and internal layout. Contextual codes are magenta satellites and dashed associations added afterwards. They exert no force on main codes. Technical depth and emotion are also overlays: neither changes grouping.

The default support threshold is three shared topic groups; a selector offers two for finer detail. There are 265 main codes with coverage of at least three groups and 606 with coverage of at least two. The three-topic model is calculated on its original 265-code family; the two-topic model is separately calculated on 606 codes. These are independently optimised fixed partitions, not a display-only filter. A shared 606-code index lets the browser replay both models. The 3,315 codes with only one topic cannot satisfy either recurrence rule, but all 3,921 main codes remain searchable. Further isolates depend on the selected connection rule. No low-frequency code is assigned a theme merely because it was included.

In the default shared-topic view, 3,315 main codes occur in one topic group and 341 in two. Another 131 of the 265 potentially eligible codes have no partner with three shared groups. This gives 3,787 unlinked codes and 134 linked codes. The threshold describes recurring cross-topic relationships; it is not a significance judgement about the importance of a code. For example, wearables_publication_fee occurs in 251 messages but only two topic-label groups, so it cannot meet this rule.

Source and grouping unit

The normalized manual Decentraland JSON has 5,000 message records. The network reads semicolon-separated labels in descriptors, deduplicated within each message. Distinct non-empty thread_topic strings define 723 groups, and a main code is counted once per topic group regardless of repeated messages. The parser retains the same last-key-wins convention as the preceding audited analysis.

A topic-label group is an operational proxy for a conversation. Repeated labels can pool separate exchanges. Associations therefore refer to cross-topic-group recurrence rather than verified independent conversational episodes. The whole-conversation overlay includes all coded message records assigned to an associated topic label; it does not reconstruct uncaptured Discord messages, external links or separate thread boundaries.

Three explicit mathematical connection rules

Let f(A) be the number of topic groups carrying code A and C(A,B) the number carrying both. Jaccard overlap is C(A,B) / [f(A) + f(B) - C(A,B)]. It accounts for relative coverage and is the attraction weight in all views.

1. Shared-topic overlap retains pairs sharing at least the selected two or three topic groups. Three is the default. This is the direct mathematical association map.

2. Enriched overlap additionally checks whether the observed overlap exceeds a frequency-based random-reference expectation. Conditional on f(A), f(B) and 723 groups, the null assigns each code uniformly over groups while fixing its total coverage. The one-sided hypergeometric tail is P(X ≥ C). This is equivalent to the enrichment direction of a fixed-margin 2×2 overlap test. BY-adjusted p-values are calculated over all potentially eligible main-code pairs before the support threshold is applied: 34,980 pairs for the 265-code three-topic model, or 183,315 pairs for the 606-code two-topic model. Retain adjusted p ≤ 0.05 and at least the selected number of shared groups; retained weights are still Jaccard. Because the correction family changes, enrichment edges at two topics are not necessarily a superset of those at three. BY is the Benjamini–Yekutieli correction, chosen to accommodate arbitrary dependence among pair tests under valid marginal p-values. See the hypergeometric definition and SciPy's multiple-testing documentation.

3. Repeated message co-coding retains pairs appearing together in the same message in at least the selected two or three distinct topic groups. Its weight remains topic-level Jaccard. This addresses closer coding association than simply occurring somewhere in the same topic.

The enriched view is a diagnostic under an explicit reference model. The uniform-assignment null does not preserve each topic's number of codes, topical richness, coding dependence or historical dependence between exchanges. BY corrects the multiple-testing problem; it cannot repair a poorly fitting null. Accordingly, these are model-based enrichment indicators, not population-level evidence that themes objectively exist. The support threshold and code classifications are visible analytical choices. A later sensitivity analysis could use a bipartite degree-preserving permutation null.

Fixed communities

Changing the support selector loads the corresponding precomputed fixed model and resets the procedural build. Community numbers are local to a model: C1 at two topics need not contain the same codes as C1 at three. Community profiles and supported contextual associations are recalculated for each new partition. Baselines and the main/contextual classifications stay the same. Two-topic recurrence is weaker evidence of cross-topic repetition; use it as a sensitivity view and inspect the underlying exchanges.

Optional high-frequency outlier layer

Here outlier means a main code with no supported edges in the selected fixed model and at least the chosen number of coded messages. This is a user-controlled descriptive inclusion rule, not a statistical anomaly test. The default floor is 100 messages, adjustable down to 25. Coverage of two topics is not required for this layer: an intensive one-topic concern may be analytically important. A code that gains a supported link under another model is displayed as an ordinary main node there, rather than duplicated as an outlier.

For each qualifying code, calculate its shared topic count and Jaccard overlap with every fixed community's topic union. The list reports its strongest overlap; a focused community can show any qualifying outlier sharing at least one of its topics. A zero-overlap code remains inspectable without an attachment. Hollow amber diamonds have area proportional to message count, subject to minimum and maximum sizes. Up to twelve diamonds appear around the map; the full list is in the outlier panel and selecting a code brings it into view. Diamond positions are an illustrative outer ring. Dotted amber lines indicate exploratory topic-union overlap; they are neither supported main-network edges nor theme membership. A high message count reflects coding intensity within the captured exchanges, not independent corroboration across conversations.

Outliers do not alter Leiden communities, live modularity, forces, anchors or community profile membership. Their overlay uses the completed archive in both maps, even during partial ingestion. Exports record the support threshold, message floor, overlay state and measured outlier associations. For example, wearables_publication_fee (251 messages in two topic groups) is available as an outlier under the default three-topic rule. Inspect its position under the two-topic rule rather than assuming that high frequency guarantees a supported link.

Fixed community calculation

The completed weighted main-code graph is partitioned with Leiden, using the RB configuration/modularity objective at resolution 1. Twenty seeds are run; the highest-modularity result is the reference. Community display numbers are ordered by size. Codes with no edges are reported separately, rather than pooled into a false community. Leiden is an established network community-detection method; see Traag, Waltman and van Eck (2019).

The reference is displayed as community circles, all linked main codes within coloured boundaries, or a focused community. Centres and gaps are arranged for navigation; maps with more than twelve communities use a spaced grid. Zoom and open a community for detail. Internal code positions use a weighted NetworkX spring layout with 400 iterations and a fixed seed. Overview circle area reflects number of linked main codes. Code-node area reflects topic coverage, with minimum display sizes. Up to 120 strongest main edges are drawn in an all-code view and 180 within a focused view. All edges enter the partition and evidence tables. Labels are limited at overview zoom to reduce collisions; zoom and the code selector give access to exact labels. Display spacing is not an independent statistical result.

Anchors are the three codes with the greatest within-community weighted strength, with topic coverage and label used to break ties. They identify central members of the graph, rather than supplying final theme names.

Slow procedural build and its comparison

The browser reprocesses the topic-level descriptor incidence supplied by Python. Topic blocks are either shuffled with a reproducible seed or processed in topic-label order. Each admitted block updates unique code coverage, shared-topic counts and repeated message-pair counts. It then recalculates Jaccard weights under the chosen support rule. These operations mirror the completed Python network.

Default speed is one topic every 450 milliseconds: roughly 5.4 minutes to ingest 723 topic groups, followed by additional settling. Speed is adjustable from 0.10 to 1.50 seconds per topic. Start, Pause, One topic, Finish ingestion and Restart make the procedure inspectable. A node grows with accumulated topic coverage. Main-node attraction uses current supported Jaccard; pair repulsion, a small centring force, velocity damping and bounded motion determine positions. This is a transparent force-directed visualization inspired by established graph layouts, with its exact force equations in viewer.js. It is not an implementation of ForceAtlas2; the ForceAtlas2 paper provides background on attraction/repulsion approaches.

Live memberships are recalculated every twelve admitted topics and at full ingestion using a separate multilevel Louvain-style modularity optimiser implemented in JavaScript. It starts from singleton communities, applies weighted local moves up to fifteen passes per level and aggregates communities for up to eight levels. A move maximises the node's weight into a group minus its degree times the group's weighted volume divided by total weighted volume. Aggregated self-loops preserve internal edge weight. Live colours come from these memberships. The procedure does not attract nodes to the reference Leiden centres, interpolate toward a fixed final layout, or reuse fixed memberships as live colours.

For the enriched option only, final-archive BY-qualified edges form a declared eligibility gate for the animation. The stream gradually reveals weights within this qualified graph. This avoids presenting repeatedly tested partial archives as independent significance results, but also means the enriched replay uses future full-archive eligibility information. Use the default broad-overlap animation to explore associations without that gate.

At full ingestion all weighted edge counts must agree with the corresponding fixed Python graph, whatever the shuffle order. This equality follows from commutative counting. Position convergence and identical community partitions do not follow: the live algorithm and Leiden differ, both optimisation and force motion can have multiple solutions, and the order changes the path. The viewer reports live modularity Q and adjusted Rand index (ARI) against fixed memberships on linked reference nodes after full ingestion. Reset with another seed to inspect sensitivity. Colour numbers between the two views are separate identifiers; compare member labels and ARI.

This is a procedural robustness visualisation, not historical temporal thematic analysis. Topic-label order is not chronological order, and admitting a topic block brings in all its coded messages at once. A future time-window analysis should explicitly filter by timestamps before rebuilding associations and profiles.

Contextual information

For a fixed community, take the union of topic groups containing at least one member main code. A contextual code's association is Jaccard between that union and its own topic coverage. List every contextual code sharing at least the selected two or three groups; display the ten strongest as magenta satellites. Individual dashed links require that same support between a contextual code and the relevant main code. Satellite positions are arranged on an outer ring and are illustrative. The same layer can be shown over the live map for the selected fixed community; this is final-archive context, rather than a partial-stream contextual estimate.

Because prevalence can produce broad context associations, contextual Jaccard measures should be read as coverage information. They are not included in the BY main-code family, community detection or forces.

Open a community and use Show contextual codes directly above either map, or the checkbox in the top toolbar. These controls stay synchronised. In broad-overlap C1, 60 contextual codes meet the community-level support rule; ten are drawn on the map. The complete list is under Member and contextual codes below the emotional profile. An unstarted animation has no admitted main-code evidence, so use the fixed map to see the completed association layer immediately.

Technical depth at the conversation level

The default group profile includes every message in the union of its associated named topic groups, counted once within that community. An alternative selector restricts the profile to messages carrying at least one member main code. The technical-depth mean is the arithmetic mean of valid manual technical_depth values 0, 1 and 2 in that selected message set. The display also reports the 0/1/2 distribution, valid-score coverage and difference from the overall mean. A source value 4 in message record 2602 is flagged and excluded; it is not silently recoded.

The default overall comparator is the entire 5,000-record archive, with 4,999 valid scores and a mean of 0.3848769754. A second comparator uses only messages assigned a named topic group. The same selected comparator is used for the emotional bars. These are message-weighted averages, matching the preceding technical-depth graphs: longer conversations carry more weight. Means assume equal spacing between the ordinal 0–2 levels and are descriptive. No significance test of the group-versus-overall difference is applied, especially since the group is a subset of its comparator.

Community profiles overlap whenever topic labels contain codes from several communities. Messages are deduplicated inside each community but can occur in several communities' profiles. The profiles therefore cannot be added together as a disjoint partition of the archive. Similar emotional or technical profiles across communities may reflect this shared conversational context.

Emotional balance: the existing eleven-category composition

The manual Decentraland mapping, category colours and typo aliases are taken from the existing Emotion category mapping.json. The categories are Violent, Dark humor, Shock, Disappointed, Skeptical, Annoyed, Defensive, Respectful, Light humor, Friendly and Excited. The mapping is retained without an LLM reassignment.

Split emotion labels on semicolons, apply the recorded aliases and deduplicate categories within each message. A message can contribute to more than one category. Divide each category's count of messages by the sum of all eleven category-message counts in the selected message set, matching the preceding composition graphs. Neutral is outside these eleven shares; retain any non-neutral categories that co-occur with it. Neutral-message counts, multiple-category counts and unmapped-tag coverage are displayed separately. An empty mapped profile has undefined shares rather than a fabricated 0% composition.

Paired bars show the community's category share and the selected overall comparator. This profile is what emotional balance means here. No single valence score is invented: categories such as shock, humor or defensiveness are not unambiguous positive/negative states, and their numbered order is not a validated psychological scale. These are coded expressions in messages, not measurements of contributors' internal mental states.

Stability and diagnostic indicators

Fifty bootstrap resamples draw the 723 topic groups with replacement, rebuild the selected graph and rerun Leiden, separately for all three connection rules at both support levels. Duplicated groups contribute repeatedly in each resample. The enriched view recalculates its hypergeometric tails and BY adjustment in each resample within the same declared family for that support level (265 codes for three topics; 606 for two). Code-pair co-assignment is measured conditional on both codes being present. Bootstrap ARI compares membership only among present reference-linked codes; structurally isolated codes cannot inflate it. Seed ARI compares the twenty reference-graph optimisations on linked codes. Fifty resamples are an initial sensitivity diagnostic, not precise interval estimation. Supported-edge co-assignment scores are exported sparsely; the within-group and outside-group summaries use the full pair matrix during calculation.

Weighted modularity Q reports connection concentration relative to the configuration reference; it has no universal pass mark. Internal weight share reports the proportion of community members' weighted connections staying inside. Conductance divides boundary weight by the smaller of community and complement volumes; lower indicates a more distinct boundary. Mean resampled co-assignment describes member-pair persistence; outside-group co-assignment gives a comparison. ARI equals 1 for identical partitions and is near 0 for agreement near its chance reference. Resolution sensitivity at 0.5, 1 and 1.5 is retained in analysis.json.

Neither Q, ARI nor visual separation establishes an interpretive theme. The mathematical map supports transparent pattern discovery; the researcher still develops a shared organising interpretation, reads counterexamples and relates it to the theoretical framework. See Braun and Clarke's guidance on reflexive thematic analysis.

Full-screen viewing and high-resolution PNG exports

The gradual-build map, fixed map and community conversation-profile panel each have Full screen and PNG buttons. The same controls are present in START_HERE.html, FIXED_MAP.html and ANIMATED_MAP.html because these files use one shared viewer template. Full-screen maps use a larger label budget with collision checks and retain fit, zoom, drag, overview and contextual controls; the animated pane also retains play, pause and one-topic controls. Escape exits. If the browser cannot enter native full screen, an expanded viewport provides the same pane controls.

Map PNGs are newly rendered at 6,000 pixels wide with a height that grows to accommodate the complete code key. The export fits the complete selected view independently of screen zoom or pan. A fixed community overview expands to all linked main-code nodes for its export, retaining computed communities and their internal spring coordinates while placing community centres on a spaced print grid. A focused fixed map exports that community. The animated map exports the current admitted evidence and live positions; it does not finish ingestion or replace live memberships with fixed ones. No export changes counts, weights, memberships or the running simulation.

Main-node area reflects topic coverage subject to display-size limits. Amber diamond area reflects message count subject to display limits. If contextual information is enabled in a focused community, the export includes all supported contextual codes, rather than the ten-satellite screen limit. When outliers are enabled it includes all qualifying outliers relevant to the selected view, rather than the twelve-diamond screen limit. These remain final-archive descriptive overlays, even on a partial animated snapshot. Individual supported contextual associations are dashed; exploratory outlier attachments are dotted and kept separate from the main graph. Community layout and overlay rings are display arrangements, not new statistical measurements.

The PNG attempts unabridged labels with collision checks and short leader lines. Where a full name cannot fit, it attempts a numbered reference, with side callouts for crowded nodes. Thin label leaders connect text to its code node and are not network edges. A complete numbered key below the graph contains every exported code's full name, type/community, message count and archive-topic coverage, including crowded nodes without room for on-map text. Long code names wrap without deletion. The image reports its code and label counts, selected support, connection rule, build stage and generation time. This avoids claiming that hundreds of labels are all readable simultaneously at normal screen size: the large image can be inspected at its native resolution, and focused-community exports provide more space per code.

The profile PNG is 6,000 × 3,600 pixels. It shows technical-depth means and score distribution, the eleven emotional-category comparisons and their coverage notes under the current profile scope and comparator. The exporter reads the existing profile; it does not derive a new emotion score. Browser memory and image handling can limit extremely large exports; the pane reports an encoding failure if one occurs. Pixel dimensions describe image resolution, not a guaranteed physical print size or DPI.

Files and reproduction

START_HERE.html is an offline, self-contained comparison viewer. analysis.json contains input provenance, all main-code counts and topic IDs, eligible matrices as edge lists, reference memberships, co-assignment diagnostics, message excerpts and profiles. models_by_support contains both sets of models; models is an alias of the default three-topic set for older readers. classification_snapshot.json records the main/contextual split. The three original community and edge CSV pairs describe the default three-topic models. Files prefixed support2_ describe the two-topic models.

build_analysis.py reads the workbook and normalized JSON directly, computes the models and invokes write_outputs.py to package all views. Its optional --root selects the workspace and --bootstrap controls the resample count. requirements.txt lists the Python packages; the supplied workspace also has them in work/gravity_runtime. The base seed is 20261008. write_outputs.py can also regenerate the standalone HTML and explanatory pages from saved analysis.json, viewer_template.html, viewer.js and map_exports.js without repeating the calculations. Re-run build_analysis.py after source or classification changes. The HTML does not read a live Excel workbook.

FIXED_MAP.html opens directly in the fixed-map view; ANIMATED_MAP.html opens directly in the procedural view. Both share the same analysis and can switch to the comparison workspace. The new files are in their own folder. Earlier maps remain available. Excel had the edited source workbook locked, so the DAO correction was saved as DCL_codes_reconciled_v3.xlsx in this folder; the new analysis reads that corrected copy. A pre-edit backup is in work/code_normalization_review.
